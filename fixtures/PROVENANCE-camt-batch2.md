# Provenance of the camt batch 2 fixtures

94 more camt messages, the latest version of the remaining message families of the Cash Management business area (batch 1 was
camt.029, 052, 053, 054, 055, 056). They are generated in two parts of 47 (`camt-batch2a`, then `camt-batch2b`); the list of all 94 is in
`tools/spec-extract/messages.json`. Captured 2026-10-11 from the **staging** ISO 20022 MCP's **resources**. No tool calls, no
snapshot, no XSD.

## How the fixtures were produced
Everything is generated by script, nothing is retyped:

1. The dictionary pages (`iso20022://dictionary/<Kind>/details?take=2000&includeDefinition=true` for `MessageComponent`,
   `ChoiceComponent`, `CodeSet`, `Text`, `Amount`, `Binary`, `Date`, `DateTime`, `IdentifierSet`, `Indicator`, `Quantity`,
   `Rate`, `Time`, `Year`, `YearMonth`, `Month`, `ExternalSchema`) and the area page
   (`iso20022://element/<Cash Management>/details?...`, which nests every message with its blocks, rules and identifier) were
   pulled page by page. The harness saves a large resource page to a file; that file is the input. A small kind that came back
   inline was recovered byte for byte from the session record, not retyped.
2. `node src/cli.ts resources write --pages <dir> --messages <list.json> --rules-tag <name>` (tools/spec-extract) reads the pages
   and writes `message.json`, `complex-types.tsv`, `snapshot-raw.tsv`, `choice-defs.tsv`, `codeset-defs.tsv`, `simple-types.tsv`,
   `codesets.tsv`, `codedefs.tsv` per message, `rules/constraints-<name>.tsv` and `rules/constraint-expressions-<name>.tsv`,
   and adds to `member-order.tsv` and `code-order.tsv`.

## What the resources gave that the snapshot did not
| Needed | Source |
|---|---|
| Message identifier and body tag | the message's `messageDefinitionIdentifier` child and `xmlTag` |
| Cardinality of every member and block | `minOccurs` / `maxOccurs` |
| Business rules: text and expression | `constraint` children (`definition`, `attributes.expression`) |
| Code wire values and enum names | `code` children (`codeName`, `name`) |
| Member, variant, block and code **order** | the order the resources list them, which is the specification's order |
| Whether a code set is external, has members, and its base set | `isExternal`, `hasMembers`, `restrictionOf` |

The order files (`member-order.tsv`, `code-order.tsv`) used to be derived from ISO's XSDs as an independent check, because the
snapshot listed members alphabetically. The resources list them in specification order, so they now come from the resources;
the existing lines (from the XSDs) are merged with what the resources say and a type listed differently is an error.

## How the reader was checked
- **Order against the XSDs.** Before batch 2, the resources were compared with the committed XSD-derived data: all 43 messages'
  building blocks, 466 component and choice types (2,554 members: names, order, tags, type references, min and max), 358 rules
  (id, text, expression), 79 simple types, and 109 enumerated code sets (wire values, names, order): 0 differences.
- **Parity.** Fixtures for the 43 existing messages were regenerated from the resources into a scratch copy and run through the
  generator. The generated model is identical in structure, order, cardinality, rules, rule code lists and code values. What
  differs is text rendering only: a line break inside a definition is now `|` where an older capture had a space, a trailing line
  break no longer leaves a trailing `|`, 20 external code-set definitions and 2 amount definitions are present that the older
  capture lacked, and four generic definitions of the two parts of an amount (`Amount of the transaction.`, `The currency in
  which this amount is measured.`) are not in the resources (they stay in the existing fixtures).
- **XSD check afterwards (not a source).** ISO's XSDs for the new messages were fetched only to test the result: the opt-in `apps/demo-shared/test/xsd-sequence.test.ts` serializes every message with every field present and validates it against its XSD (all messages pass, structure only), and `spec-extract order --xsd` reports no member or code order that differs from the resource-derived order files.
- Each of the 94 messages' identifier, name and body tag in the resources matches what was captured earlier by `universal_lookup`
  (0 differences).

## Not generated yet
- Rules on simple types, amounts and code sets (for example `IBAN`, `ActiveCurrency`): the resources list them as prose without
  expressions. They are read but not written to the fixtures.
- The camt families with a second flavour (`camt.007.002`, `camt.008.002`) were not chosen; their `.001` flavours are in batch 2.
